# PV Triage Assistant

**医薬品安全性監視（PV）の一次評価支援ツール。有害事象報告を読み、重篤度・既知/未知・因果関係の評価ドラフトを根拠付きで作成し、人が承認します。**

🌐 [English](README.md) ｜ **日本語**

**デモ:** [日本語](https://h4b6m4zyqj.ap-northeast-1.awsapprunner.com/ja/triage) ・ [English](https://h4b6m4zyqj.ap-northeast-1.awsapprunner.com/en/triage) ・ [ケーススタディ](https://h4b6m4zyqj.ap-northeast-1.awsapprunner.com/ja/about)（課題・設計判断・評価で言えること言えないこと）

登録不要です。公開デモは同梱の合成症例（または症例ビルダーで作った症例）で実際のパイプラインを動かします。有料のLLM APIを呼ぶため、実行回数を制限し、ファイルのアップロードは受け付けていません。

## 作り方

**きっかけ:** 大学院（NTU 修士課程）で LLM や RAG などの AI 技術を学び、それを以前の仕事である PV の業務に当てはめるとどこまでできるかを試したかった。PV の一次評価では、届いた報告ごとに同じ観点での判断を繰り返す。その一方で、過小評価をすると報告漏れになり、規制上許されない。そのため、LLM に判定をすべて任せることはしなかった。「症例を読み解くのは LLM、最終的な判定はルールと人」という役割分担にし、すべての判定に根拠を付けることを重視した。最初は報告書に質問できる RAG の Q&A として作り始め、実際の業務の流れに合わせて一次評価のワークフローへと広げた。

**役割分担:** 課題設定（PV の一次評価のどこを支援するか、何を最優先にするか）は、作者が自分の実務経験をもとに行った。設計と評価は、AI（Claude Code）との壁打ちで検討し、採否は作者が判断した。設計で検討したのは、LLM とルールの分担、処理の流れ、人による承認の仕組み、ローカルモデルを使う範囲、Web・クラウド構成。評価で検討したのは、正解データの作り方、採点の観点、結果から言えることと言えないこと。正解データは LLM で下書きし、作者が PV の実務経験をもとにレビュー・修正した。実装・テストコード・文書の下書きには AI コーディング支援を使った。主な設計判断は [docs/adr/](docs/adr/)、評価は [experiments/](experiments/) に、再現できる形で残している。

## なぜ作ったか

安全性部門は、届いた報告ごとに「重篤か」「添付文書に記載があるか」「因果関係を否定できるか」を判断し、期限内に報告しなければなりません。この領域は非対称で、**過大評価はレビューの手間で済みますが、過小評価は報告漏れになります**。そこで次の3つを、機能ではなく設計上の制約として扱っています。

- **過小評価をしない。** 不確実な判定は安全側（要確認／否定できない）に倒し、黙って決めずに人に見せます。
- **すべての判定に出典を付ける。** 症例本文の引用、該当したICH E2Aの基準、照合した添付文書の箇所のいずれかです。
- **決めるのは人。** システムはドラフトを作り、レビュアーが承認します。変更は元の値を残して監査証跡にします。

題材は自分のPV実務経験（有害事象評価、日英の規制文書作成）から選びました。すべての設計判断を自分の言葉で説明できることを目標にしたポートフォリオです。

## 何ができるか

1. **症例のトリアージ**（PDF／テキスト／メール／スキャン画像）— 自社品判定のゲート → 患者と有害事象の抽出（*経過からしか読み取れない事象も含む*）→ MedDRA PTのコード化 → 重篤度（ICH E2A）・既知/未知（添付文書との照合）・時間的な因果関係を並列に判定 → 過去の承認症例との整合確認。
2. **レビューと承認** — 実行はレビュー待ちで一時停止します。レビュアーは判定の上書き、抽出の修正、医学的に重要な事象（IME）リストへのPT昇格ができます。承認した症例は以後の判例になります。
3. **コストの表示** — 実行ごとに、ステップ別のトークン数・費用（USD）・処理時間を実測して表示します（サンプル症例で約 **$0.03〜0.04・15〜18秒**）。
4. **質問（RAG Q&A）** — 報告書を索引化して質問すると、出典付きで回答します。このプロジェクトの出発点です。

## 評価

手作りの正解データ（gold）に対して、安全性を重視した観点（過小評価を最優先）で採点しました。詳細は [experiments/EVALUATION.md](experiments/EVALUATION.md)。

| | 結果 |
|---|---|
| **過小評価**（重篤度・因果・既知/未知） | **0件** — 本評価、3回の反復実行、未知症例（ホールドアウト）、難症例のすべてで |
| MedDRA PTのコード化 | **100%**（23/23）— 単一LLMの比較対象は29% |
| 既知/未知 | **100%** — 単一LLMは過小評価が3件、本パイプラインは0件 |
| 重篤度 | **83〜91%**（複数回の評価の範囲：主評価83〜87%、反復87〜90%、比較実験91%）— 不一致はすべて安全側の過大評価 |
| 自社品ゲート | 評価対象外の2症例を、評価を始める前に正しく停止 |

**この評価で言えないこと：** 標本は小さく（合成7症例、うち評価対象5症例・23事象）、正解データはLLMで起案しPVの実務家が修正したもので、独立した2人目の判定者による検証はしていません。「過去症例のフィードバックで精度が上がる」は**実証できませんでした**。未知症例では判例は何も変えず、以前見えた改善は初期データ（seed）に依存したものでした。重篤度と因果は単一LLMでも健闘しており、本パイプラインの優位が測定できたのは MedDRA と既知/未知、そして過小評価を出さないことです。

## アーキテクチャ

```
症例報告（PDF / テキスト / メール / 画像）── 取り込み: pdfplumber + NFKC, .eml, OCR
    │
    ▼
product_match ──── 自社品なし ───► out_of_scope   （ここで終了、$0）
    │
extraction  （報告された事象 + 経過から読み取った事象）
    ├──► meddra ──► seriousness     ICH E2A：LLMが基準を読み、ルールが判定
    ├──► causality                  時間的・既定は保守的
    └──► expectedness               添付文書へのRAG + 確信度ゲート
                  │（合流）
                  ▼
precedent ──► influence（IMEリスト・過去症例）──► human_review ⏸ ──► finalize（監査証跡）
```

エージェントではなく LangGraph のワークフローで、3つの判定は並列に動きます。レビュー待ちは LangGraph の `interrupt` で、チェックポイントに保存されるため再起動しても再開できます。

**デプロイ構成:** ブラウザ → **Next.js**（UI ＋ BFF）→ **FastAPI** → OpenAI。**AWS App Runner**（東京リージョン）上の2コンテナです。ブラウザはAPIを直接呼ばず、Next.jsのサーバーが共有シークレット付きで中継します。そのためCORSが不要で、それ以外からのAPI呼び出しは403で拒否されます。同じイメージが `docker compose up` でローカルでも動きます。

## 設計判断

詳細は [ADR（設計判断記録）](docs/adr/) にあります（背景・選択肢・決定・結果。根拠となった実験へのリンク付き）。

- **LLMが読み、ルールが決める。** 重篤度は、モデルがICH E2Aの各基準について経過を読み（婉曲表現や、どの事象が入院の原因かの帰属を含む）、決定的なルールが判定に変換します。既知/未知は、モデルが一致の種類を分類し、ゲートが 既知／要確認／未知 に対応付けます。判定を監査できる状態に保つためです。[ADR 0002](docs/adr/0002-expectedness-confidence-gate.md)、[0004](docs/adr/0004-seriousness-e2a-llm-plus-deterministic.md)
- **MedDRAはハイブリッド検索。** 文字2-gramのBM25とベクトル検索をRRFで統合し、完全一致は決定的に即決します。日本語の形態素解析器は不要です。[ADR 0003](docs/adr/0003-meddra-retrieval-hybrid.md)
- **エージェントではなくワークフロー。** 手順と順序は業務で決まっているため、道具を選ぶエージェントより固定のグラフの方が説明もテストもしやすいです。[ADR 0006](docs/adr/0006-langgraph-orchestration.md)
- **以後の症例を変えるHITL。** PTをIMEリストに昇格すると、以後そのPTの事象は自動的に重篤になります。承認症例は判例になりますが、判定を動かせるのは安全側だけです。[ADR 0007](docs/adr/0007-hitl-approval-interrupt.md)〜[0010](docs/adr/0010-past-data-influence-mode.md)
- **コスト／プライバシーを測って決める。** 埋め込みと生成はステップ単位で差し替えられます。ローカルモデル5種をステップ別に比較したところ、7〜8Bでは過小評価0を保てるものがなかったため、ローカル構成は「転記・コード化はローカル、臨床判断は高性能モデル」のハイブリッドにしています。[ADR 0011](docs/adr/0011-local-embedding-provider.md)、[0012](docs/adr/0012-local-generation-per-step.md)
- **BFF構成。** 最初のStreamlit UIをNext.jsに置き換えましたが、APIが最初から分離していたので、バックエンドの変更は不要でした。[ADR 0013](docs/adr/0013-nextjs-frontend-bff.md)
- **MedDRAはリポジトリに含めない。** MedDRAはライセンス製品のため、リポジトリには架空のデモ用語集だけを置いています。ライセンスを持つ組織は `MEDDRA_PATH` に自社のMedDRA/J ASCIIファイルを指定すれば使え、ベクトル索引も自動で作り直されます。[ADR 0014](docs/adr/0014-meddra-not-bundled.md)
- **デモの保護はサーバー側で強制。** サンプル限定の入力はBFFで強制します（症例ビルダーは項目だけを送り、報告本文はサーバーが組み立てる）。IPごと・1日ごとの上限に加え、LLM事業者側に支出上限を設けています。
- **コストは推定ではなく実測。** グラフの実行に付けたLangChainのコールバックが、トークンと時間をステップごとに集計します。各サービスは計測されていることを知りません。
- **日英対応の線はモデルの手前で引く。** `/en/` ではUI・決まった語彙・MedDRAの用語を英語にし、症例本文とモデルの判定根拠は日本語のままです（パイプラインと評価が日本語のため）。レビューフォームは「Needs review」と表示しつつ `要確認` を送り、それをテストで保証しています。
- **理解してから加速する。** 最初のRAGはOpenAIとChromaのSDKを直接使って書き（タグ `v0.1-scratch-rag`）、その後LangChainへ移行しました。

## ローカルで動かす

Docker と OpenAI の APIキーが必要です。

```bash
git clone https://github.com/nabeofchanKo/pv-rag-assistant.git
cd pv-rag-assistant
cp .env.example .env        # OPENAI_API_KEY を設定
docker compose up --build   # UI :3000、APIドキュメント :8000/docs
```

ローカルではアップロードが有効です（`DEMO_MODE=0`）。公開デモでは無効にしています。

### テスト

```bash
venv/bin/python -m pytest backend/tests -q                        # 181件
cd web && npx playwright install chromium && npm run test:e2e     # ブラウザテスト7件
```

- **バックエンド:** フェイクを使った単体テスト（APIを呼ばない）。**安全性のゲート**は、決定的な判定層が受け取りうる入力をすべて試し、モデルがどう出力しても過小評価にならないことを証明します（モデルは解釈するだけで、決めるのはコード。そのため不変条件は構造上成り立ち、残りを評価で測ります）。さらに、Pydanticのモデルと TypeScript の型を同期させる**契約テスト**があります。
- **E2E:** 実際のブラウザと実際のBFFを、**本物のバックエンドから録画した応答**を返す偽バックエンドに対して動かします。無料で結果が毎回同じです。承認時にBFFが送る内容が、本物のバックエンドが受理したものと完全に一致することを、日英両方で確認します。録画し直すときは `web/e2e/record_fixtures.py` を使います。

## API

| メソッド | エンドポイント | |
|---|---|---|
| `POST` | `/cases/triage` | 症例をトリアージ → レビュー待ちのドラフト（または `out_of_scope`） |
| `GET` | `/cases/{thread_id}` | ドラフトまたは確定結果を再取得 |
| `POST` | `/cases/{thread_id}/approve` | 上書きを添えて承認／却下 → 結果と監査証跡 |
| `POST` | `/documents/upload` | Q&A用に文書を索引化 |
| `POST` | `/query` | 質問 → 回答と出典 |

スキーマの詳細は `/docs`（OpenAPI）にあります。

## 制約

- **評価の規模が小さい**（[評価](#評価)参照）。実行ごとのばらつきは3回の実行で測っており、信頼区間は出していません。
- **入力は日本語のみ。** パイプライン・参照データ・正解データは日本語です。英語版UIが訳すのは画面であり、モデルの出力ではありません。
- **デモの状態は保存されない。** レビュー中のスレッド、判例、IMEへの昇格はコンテナ内にあり、デプロイで消えます。移行方法（Postgresのチェックポイント）はADR 0013に記載のみで、未実装です。
- **E2Eは録画した応答を再生する**ため、UIとBFFの退行は検出できますが、バックエンドの判定内容の変化は検出しません（それは評価ハーネスの役割です）。

## データ

症例はすべて本プロジェクト用に作った**合成データ**で、実際の患者データは含みません。添付文書は架空のものです。

**このリポジトリにMedDRAは含まれていません。** MedDRA®はICHの登録商標で、利用にはMSSO（日本語版MedDRA/JはJMO）との契約が必要です。MedDRAコード化のステップは、架空のデモ用語集（[data/terminology/demo_pt.csv](data/terminology/demo_pt.csv)、56語）で動いています。コード（`DEMO-0001` …）と器官別の分類はこのプロジェクト用に作ったものです。用語名は一般的な臨床用語で、一部はMedDRAの表記と一致します。本物の辞書を使う場合は、契約して入手したMedDRA/J ASCIIファイル（`pt.asc`、`pt_j.asc`、任意で `mdhier.asc`・`soc_j.asc`）を `data/meddra/`（gitの管理対象外）などのフォルダに置き、`MEDDRA_PATH` にそのフォルダを指定してください。詳細は [ADR 0014](docs/adr/0014-meddra-not-bundled.md) にあります。
